# Venu Skill Runtime — Architecture (Phase 1)

This document covers what Phase 1 actually implements: the registry schema,
the canonical/cross-cutting distinction, and the 5-tier evidence model that
governs how the runtime's evaluation results may be described. The full
15-component target architecture (router, composer, policy engine,
authorization, tool/MCP gateway, execution controller, etc.) is described in
`docs/PHASE0-ASSESSMENT.md` and is **not** implemented yet — Phase 1 is
registry + loader + validator only.

## Canonical vs. cross-cutting: a load-bearing distinction

The Skill library contains 58 packages, split into two kinds that must never
be collapsed into one flat list:

- **Canonical Skills (53)** — domain Skills the runtime routes tasks to.
  Split further into two source-evidenced categories (per `README.md`):
  - **Technical/AI (47)** — engineering, infrastructure, trading, creative,
    and agentic-systems domains.
  - **Business Mastery (6)** — `commerce-trade-mastery`,
    `entrepreneurship-mastery`, `integrated-business-strategy`,
    `legal-law-mastery`, `marketing-management-mastery`,
    `risk-management-mastery`. These use a different, additional test format
    (`references/sources.md` + `tests/cases.md`, a 15-item narrative
    checklist oriented at legal/financial rigor) rather than the 47
    technical Skills' "10/10 Operating Contract" template.
- **Cross-cutting extensions (5)** — `aar-loop-reflexion-evolution`,
  `llm-mcp-guardrails-mastery`, `voice-agent-systems-mastery`,
  `blender-mcp-integration-mastery`, `ai-observability-telemetry-mastery`.
  These are **inheritable capability/policy modules**, not additional domain
  Skills, unless explicitly promoted later. A task is routed to canonical
  Skill(s); cross-cutting extensions apply *across* whatever is routed
  (guardrails, observability, memory/evolution behavior), not as an
  alternative routing target.

The registry's `kind` field (`canonical` | `cross_cutting`) encodes this
distinction directly. The `category` field (`technical` | `business_mastery`
| `cross_cutting`) encodes the finer, still source-evidenced split.

## Registry schema

One authoritative, generated registry replaces the two independent lists
that existed before Phase 1 (`SKILL-REGISTRY.json`'s flat name arrays, and
`benchmarks/SKILL-REGISTRY-2026-09.md`'s markdown list of 47 names only).
Generated by `venu-runtime/scripts/build_registry.py`, defined in
`venu_runtime.schemas.registry_schema`:

| Field | Notes |
|---|---|
| `id` | The Skill's **directory name** — not its frontmatter `name` field. See "Why directory name, not frontmatter name" below. |
| `version` | From frontmatter `metadata.version`. `null` where undeclared (all 6 Business Mastery Skills currently declare no `metadata` block at all). |
| `kind` | `canonical` \| `cross_cutting`. |
| `category` | `technical` \| `business_mastery` \| `cross_cutting`. |
| `maturity` | From frontmatter `metadata.maturity`, e.g. `"10-of-10-target"`. `null` where undeclared. |
| `description` | From frontmatter `description`. |
| `declared_tool_scopes` | Always `[]` in Phase 1 — no Skill in the repository currently declares a structured tool-scope list. This is an honest reflection of current content, not a placeholder to fill blindly; the Policy Engine (a later phase) is what will make this field meaningful. |
| `cross_cutting_dependencies` | Always `[]` in Phase 1. `aar-loop-reflexion-evolution` declares a free-text `metadata.inherits` field describing conceptual lineage ("aar-loop concepts + Reflexion/self-refinement research + Venu evaluation/evolution + Venu guardrails") — this is prose, not a structured, unambiguous list of specific cross-cutting Skill IDs, so Phase 1 does not attempt to parse it into this field. A later phase should either standardize a structured `depends_on:` frontmatter field, or treat this as a documented open question rather than guess at the mapping. |
| `risk_tier` | Always `unclassified` in Phase 1 — no Policy Engine exists yet to assign a real tier. |
| `benchmark_status` | Tier 1 evidence only (see below) — joined from `benchmarks/unified_benchmark_results.json` where a matching entry exists (the 47 technical Skills); `static_checks_available: false` for the 6 Business Mastery and 5 cross-cutting Skills, which that checker does not cover. |
| `provenance` | Source repository, git commit at build time, and the Skill's relative path. |
| `source_hash` | SHA-256 of the Skill's `SKILL.md` bytes, for change detection. |
| `validation_status` / `validation_findings` | Structural loadability verdict from the Skill Validator — see below. |

### Why directory name, not frontmatter name

`skills/_cross-cutting/llm-mcp-guardrails-mastery/SKILL.md` declares
`name: execution-controller-and-tool-governance` in its frontmatter — a
copy-paste leftover from another Skill's template. If the registry used the
frontmatter-declared name as the identifier, this Skill would silently
collide with the real `execution-controller-and-tool-governance` Skill's
registry entry. The directory name is filesystem-enforced-unique and is what
every other part of the repository (paths, the pre-Phase-1 registry lists,
the benchmark scripts) already uses as the real identifier, so the registry
builder uses it as `id` and records the frontmatter's (wrong) declared name
only inside `validation_findings`, as data about the file rather than as the
Skill's identity.

## The 5-tier evidence model

The static SKILL.md content checkers in `benchmarks/` (fixed for portability
in Phase 1, not rewritten) and this runtime's own validator produce evidence
at different tiers. Nothing in this repository currently produces Tier 3–5
evidence — that requires the execution/verification/evaluation components
planned for later phases. Any report that blends these tiers into one
number is misrepresenting what has actually been demonstrated.

1. **Specification quality** — does the SKILL.md content itself meet the
   documented structural/domain bar? Produced by `benchmarks/run_benchmark.py`,
   `benchmarks/unified_benchmark.py`, `benchmarks/run-skill-regression.py`.
   Text linting only — no model or tool is ever invoked.
2. **Static schema validation** — does the Skill package load correctly
   (parseable frontmatter, required fields present, name/directory
   consistency)? Produced by `venu_runtime.loader.validator` and recorded in
   the registry's `validation_status`/`validation_findings`.
3. **Runtime behavioral evidence** — did an actual execution (selected
   Skills, composed plan, tool calls, side effects, verification result)
   happen and succeed? **Not implemented.** `benchmarks/REGRESSION-MANIFEST-235.json`
   documents the intended shape (47 × 5 scenario classes; per the Phase 1
   decision, the target is 53 × 5 = 265) but every case remains
   `runtime-pending` until the Execution Controller and Evaluation Engine
   exist.
4. **Security evidence** — adversarial/prompt-injection/tool-poisoning cases
   run against the Policy Engine and Tool/MCP Gateway specifically. **Not
   implemented** — no Policy Engine or Gateway exists yet.
5. **Regression evidence** — pass/fail history per case over time, growing
   only by confirmed failures becoming durable regression cases. **Not
   implemented** — no Regression Manager exists yet.

A `unified_benchmark_results.json` report showing "517/517 passed, all
Skills at 10.0/10" is Tier 1 evidence only. It says the Skill files are
well-formed and internally consistent by the checker's own rules; it says
nothing about whether an LLM using a Skill produces correct results, calls
tools safely, or survives an adversarial input. `benchmarks/UNIFIED-BENCHMARK-FINAL-2026-09.md`
already states this limitation for itself — this document exists so the
distinction survives future summarization rather than getting lost.

## Known data-quality findings from Phase 1

The validator surfaced two pre-existing issues in the Skill library, neither
of which Phase 1 corrects (per the Phase 1 instruction not to modify Skill
content):

- `skills/_cross-cutting/aar-loop-reflexion-evolution/SKILL.md` — invalid
  YAML frontmatter (a stray leading space before `description:`).
  `validation_status: fail`.
- `skills/_cross-cutting/llm-mcp-guardrails-mastery/SKILL.md` — frontmatter
  `name:` field does not match its directory (see above).
  `validation_status: warning`.

Both remain loadable (the loader falls back to regex extraction for the
first, and the registry uses directory name regardless of the second), so
neither blocks the registry from covering all 58 Skills.
